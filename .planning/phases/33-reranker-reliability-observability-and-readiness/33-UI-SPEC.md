# Phase 33 — UI Design Contract

> Visual and interaction contract for the reranker reliability dashboard. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope and Locked Direction

This phase is a semantic correction inside the existing dashboard, not a redesign. Preserve the current card hierarchy, compact density, responsive wrapping, light/dark themes, and PT-BR language. The UI must make two different questions answerable at a glance:

1. **Did terminal requests succeed?** — `request_success_rate`, including client and governor rejections in the request-outcome denominator.
2. **Was the serving path available?** — service availability, excluding client/local validation and governor policy rejections, while counting routing, transport/timeout, upstream HTTP, and invalid upstream-response failures.

Source: `33-CONTEXT.md`, `REQUIREMENTS.md`, and the existing performance dashboard components.

## Information Architecture and Layout

### Overview health panel

Keep `PerformanceHealthPanel` full width in its current overview grid and preserve its existing header, border, radius, and 24-hour context.

1. **Header:** existing health icon, **Saúde de desempenho**, and **Métricas de desempenho das últimas 24 horas**.
2. **Primary KPI grid:** four cells in this order — **Sucesso das solicitações**, **Disponibilidade do serviço**, **Latência média**, **Throughput**. Use two columns below `sm` and four columns from `sm` upward. The two health indicators use the 16px primary value style; latency and throughput remain 14px.
3. **Outcome classes:** a compact semantic list below the KPI grid. Use one column below `sm`, two columns from `sm`, and four columns at `lg`. Each row contains the class label, terminal count, and percentage of terminal outcomes. Use a list/definition-list pattern rather than a pie or donut chart.
4. **Top models by traffic:** preserve the current maximum of six model rows and current responsive one/two-column behavior. Rename the displayed rate context to **Sucesso das solicitações**; never present it as provider or TEI health. Model names remain truncatable with the full value available through an accessible tooltip/title.

### Models dashboard performance strip

Keep `PerformanceOverview` as the existing compact bordered strip. Add **Disponibilidade do serviço** beside **Sucesso das solicitações** and preserve latency, throughput, wrapping, and the top-model badges. On constrained widths the groups wrap; they never create horizontal scrolling. Per-model badges may continue to show request success only, but their accessible name and tooltip must explicitly say **Sucesso das solicitações**.

### No redesign contract

- No new page, route, navigation item, modal, large chart, hero, gradient, animation, or dashboard theme.
- No change to card radius, shadow language, sidebar, global density, or existing theme selector.
- Do not collapse the two primary health indicators into a single composite score.
- Do not hide outcome classes exclusively behind hover. An optional disclosure may reveal definitions, but counts and class labels remain visible.

## Data and Calculation Contract

The UI consumes additive/versioned API counts and derives no aggregate from a simple mean of model percentages.

| Display value | Required calculation |
|---------------|----------------------|
| Sucesso das solicitações | `success_count / terminal_count * 100` |
| Disponibilidade do serviço | `success_count / (success_count + routing_unavailable_count + transport_timeout_count + upstream_http_failure_count + invalid_upstream_response_count) * 100` |
| Latência média geral | `total_latency_ms / latency_sample_count`; never mean of model averages |
| Throughput geral | aggregate output tokens divided by aggregate generation duration; never mean of model TPS values |
| Outcome-class percentage | class count divided by `terminal_count` |

Rules:

- One terminal request contributes to exactly one outcome class. Retries do not add a second terminal outcome.
- Routing failure before relay/channel selection is part of the service-availability denominator.
- Client/local validation and governor rejection remain visible in the outcome breakdown but do not reduce service availability.
- The UI must prefer backend-provided aggregate counts when available. If it aggregates model rows, it sums their underlying counts first and computes the ratio once.
- A zero denominator renders `—`, never `0,00%` or `100,00%`.
- Missing fields are not coerced to zero. If required counts are missing from any in-scope row and no complete overall aggregate is supplied, render `—` for the affected overall KPI and show **Dados parciais**.
- Legacy payloads that expose only `success_rate` may still render the per-model request-success value. They must not participate in a new overall weighted KPI without their underlying counts.
- Percentages use two decimal places and PT-BR decimal punctuation in the rendered PT-BR locale. Counts use locale-aware integer formatting.

### Outcome order

The visible and keyboard-reading order is fixed:

1. Sucesso
2. Validação do cliente
3. Rejeição do governor
4. Roteamento indisponível
5. Transporte ou timeout
6. Falha HTTP upstream
7. Resposta upstream inválida

## Interaction and State Contract

| State | Required behavior |
|-------|-------------------|
| Loading | Preserve the final panel height with `Skeleton`; render four KPI skeletons plus outcome-row skeletons. Do not announce temporary zeroes. |
| Loaded, complete | Render all KPIs, seven outcome classes, and top-model rows from count-derived values. |
| Loaded, partial | Render available values, replace unverifiable aggregates with `—`, and show a neutral **Dados parciais** badge with an always-accessible explanation. |
| Empty | Use the existing shadcn `Empty` composition; show the exact heading/body below and no percentages. |
| Error | Use `Alert` with `role="alert"`, concise recovery copy, and a **Recarregar métricas** button that refetches the same 24-hour query. Keep automatic query retry disabled. |
| Refetching | Keep the last valid values visible, disable the recovery action, and show its existing spinner pattern; do not blank the panel. |
| Zero class count | Show `0` and `0,00%` for the class row only when `terminal_count > 0`; this is different from missing data. |

The phase has no destructive action and therefore no confirmation dialog. No interaction writes data or changes readiness/routing state from this dashboard.

## Accessibility

- The panel is a named `<section>` whose heading is associated through `aria-labelledby`.
- KPI names and values are exposed as complete phrases to assistive technology, for example: “Disponibilidade do serviço, 100,00 por cento”.
- Outcome classes use semantic list or `<dl>` markup; visual dots/icons are `aria-hidden`.
- Tooltips supplement visible labels; they never contain the only definition, count, or recovery instruction.
- **Dados parciais**, empty, and error states are distinguishable without color. Error recovery is keyboard reachable with a visible focus ring and a 44px minimum target.
- Loading skeletons are hidden from the accessibility tree; the panel exposes a concise loading status without repeated announcements.
- Preserve `prefers-reduced-motion`; add no motion beyond the project skeleton behavior.

## Verification Targets

- Weighted totals use underlying counts and differ correctly from a simple mean when model traffic is uneven.
- The `8/9` client-validation scenario displays request success `88,89%` and service availability `100,00%` when no serving-path failure exists.
- A no-channel terminal outcome decreases service availability and appears under **Roteamento indisponível** exactly once.
- Zero-data and partial-payload fixtures render `—` where calculation is unsafe, without `NaN`, `Infinity`, or fabricated `0,00%`.
- PT-BR labels fit at mobile width without horizontal scroll; long model names truncate while remaining accessible.
- Light and dark themes retain contrast, and all outcome classes remain understandable with color disabled.
